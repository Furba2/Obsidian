# 1. The Big Picture

PostgreSQL is easier to understand if I separate these ideas:

```
Linux
  │
  ├── PostgreSQL service
  │      │
  │      └── PostgreSQL cluster
  │             │
  │             ├── databases
  │             │    ├── postgres
  │             │    ├── template0
  │             │    ├── template1
  │             │    └── mydb
  │             │
  │             └── PostgreSQL processes
  │
  └── psql / pg_ctl / oid2name / pg_dump ...
```

### The most important distinction

```
PostgreSQL cluster
       │
       ├── database: mydb
       │      │
       │      ├── table: users
       │      └── ...
       │
       └── other databases
```

I don't normally connect to a cluster and then choose a database later.

I connect to a **specific database inside the cluster**.

For example:

```
psql -U furba -d mydb -h localhost
```

# 3. `pg_ctl` — Controlling PostgreSQL

`pg_ctl` is PostgreSQL's command-line server-control utility.

Think of it as a remote control for a PostgreSQL cluster.

```
pg_ctl
  │
  ├── start
  ├── stop
  ├── restart
  ├── status
  ├── reload
  └── promote
```

## Common commands

```
pg_ctl start
pg_ctl stop
pg_ctl restart
pg_ctl status
pg_ctl reload
```

For example:

```
pg_ctl status
```

may show:

```
pg_ctl: no server running
```

After:

```
pg_ctl start
```

it may show:

```
waiting for server to start....
server started
```

Then:

```
pg_ctl status
```

may show:

```
pg_ctl: server is running (PID: 96724)
/usr/local/bin/postgres
```

### PID

PID means **Process ID**.

The operating system gives every running process a number.

```
PostgreSQL
   │
   └── PID 96724
```

# 4. `pg_ctl` vs `systemctl`

I can control PostgreSQL in two different ways, but they operate at different levels.

```
                 Linux
                   │
             ┌─────┴─────┐
             │            │
         systemctl      pg_ctl
             │            │
       system service   PostgreSQL
             │          cluster
             ▼            │
       PostgreSQL         ▼
         service       postgres
```

### `systemctl`

`systemctl` is Linux's systemd service manager.

```
sudo systemctl start postgresql
sudo systemctl stop postgresql
sudo systemctl restart postgresql
sudo systemctl status postgresql
```

It can manage many services:

```
sudo systemctl start postgresql
sudo systemctl start nginx
sudo systemctl start ssh
sudo systemctl start docker
```

### `pg_ctl`

`pg_ctl` is PostgreSQL-specific:

```
pg_ctl start
pg_ctl stop
pg_ctl status
```

For my normal Linux Mint/Ubuntu installation, I should generally let `systemd` manage the packaged PostgreSQL service:

```
sudo systemctl status postgresql
```

`pg_ctl` is especially useful when I am manually managing a PostgreSQL data directory or learning how PostgreSQL works internally.

---

# 5. PostgreSQL Must Not Run as Root

PostgreSQL normally runs as the unprivileged Linux user:

```
postgres
```

It should not be started directly as root.

Bad:

```
sudo pg_ctl start
```

PostgreSQL can reject this with:

```
pg_ctl: cannot be run as root
```

The PostgreSQL process should be owned by the PostgreSQL service user.

For a manually managed cluster, the relevant user must own the data directory.

# 6. PGDATA

`PGDATA` means the PostgreSQL **data directory**.

It contains the cluster's data, configuration, WAL, and internal state.

For a typical Ubuntu/Mint PostgreSQL 16 installation, mine is commonly:

```
/var/lib/postgresql/16/main
```

I can ask PostgreSQL for the exact location:

```
SHOW data_directory;
```

From the shell:

```
sudo -u postgres psql -c "SHOW data_directory;"
```

### Important

Don't guess the data directory.

For example, this is not automatically correct:

```
/postgres/16.15/base
```

The actual directory can be different.

# 8. Why `base` Contains Numbers

PostgreSQL does not store database and table names directly as normal filenames.

It uses numeric identifiers called **OIDs** and **filenodes**.

For example:

```
base/
├── 1
├── 4
├── 5
└── 16389
```

A directory inside `base` corresponds to a database.

Inside a database directory, files correspond to database objects.

So the disk might look like:

```
base/
│
├── 16389/       ← one database
│     ├── ...
│     └── ...
│
└── 5/           ← another database
      ├── ...
      └── ...
```

The numbers are internal PostgreSQL identifiers.

# 9. `oid2name`

`oid2name` translates PostgreSQL's internal numeric identifiers into names.

I found my executable here:

```
/usr/lib/postgresql/16/bin/oid2name
```

I added PostgreSQL 16's binary directory to my `PATH`:

```
export PATH="/usr/lib/postgresql/16/bin:$PATH"
```

To make that permanent in Bash:

```
echo 'export PATH="/usr/lib/postgresql/16/bin:$PATH"' >> ~/.bashrc
source ~/.bashrc
```

Now:

```
oid2name --version
```

should work.

### Show databases

```
oid2name -U furba -h localhost -d mydb
```

Or list databases:

```
oid2name -U furba -h localhost -l
```

The idea is:

```
OID 16384  ─────►  mydb
```

### Show a table's filenode

`oid2name` can also map a filenode to a table name.

The general form is:

```
oid2name -d mydb -f FILENODE
```

# 14. SQL vs `psql` Commands

Inside `psql`, there are two kinds of commands.

### SQL

SQL statements normally end with:

```
;
```

Example:

```
SELECT current_date;
```

or:

```

    id SERIAL PRIMARY KEY,
    name TEXT
);
```

### `psql` meta-commands

These start with:

```
\
```

Examples:

```
\q
\l
\dt
\d users
\du
\conninfo
```

These are commands understood by `psql`, not normal SQL.

# 19. Template Databases

When a PostgreSQL cluster is initialized, it normally has:

```
template0
template1
postgres
```

### `template1`

`template1` is the normal template for new databases.

Conceptually:

```
template1
    │
    ├── copied when a new database is created
    │
    ├──► mydb
    └──► another_database
```

Objects placed in `template1` can appear in newly created databases.

### `template0`

`template0` is the clean base template.

It is kept as a pristine copy.

### `postgres`

`postgres` is a normal default database commonly used for administration and initial connections.

# 20. PostgreSQL Processes

A running PostgreSQL cluster contains multiple processes.

Conceptually:

```
postgres
│
├── checkpointer
│      └── writes checkpoint data
│
├── background writer
│      └── writes dirty pages
│
├── walwriter
│      └── writes WAL
│
├── autovacuum launcher
│      └── manages automatic vacuum workers
│
├── background workers
│
├── replication processes
│
└── backend processes
       ├── client connection 1
       ├── client connection 2
       └── client connection 3
```

The exact set of processes can vary by PostgreSQL version and configuration.

### Backend process

A client connection gets a backend process.

For example:

```
psql
 │
 └── PostgreSQL backend
```

This is one reason PostgreSQL is described as using a **multi-process architecture**.

---

# 21. Why PostgreSQL Uses Processes

The source material describes several advantages:

### Isolation

If one process has a problem, it is isolated from other processes.

### Portability

The process model works across operating systems.

### Efficiency

Process creation is efficient enough for PostgreSQL's architecture.

# 22. Common Connection Problems

## Problem 1: Database does not exist

Example:

```
FATAL: database "fu" does not exist
```

Cause:

```
psql
```

was used without specifying `-d`.

Fix:

```
psql -U furba -d mydb -h localhost
```

---

## Problem 2: Role does not exist

Example:

```
FATAL: role "fu" does not exist
```

Cause:

```
psql
```

uses the Linux username by default.

Fix:

```
psql -U furba -d mydb -h localhost
```

---

## Problem 3: Connection refused

Example:

```
could not connect to server: Connection refused
```

Possible cause:

The PostgreSQL server isn't running or isn't listening where I am trying to connect.

Check:

```
sudo systemctl status postgresql
```

or, for a manually managed cluster:

```
pg_ctl status
```

Don't immediately change `listen_addresses` just because of this error. First verify which cluster is running and where it is listening.

---

## Problem 4: `pg_hba.conf` denies the connection

Example:

```
FATAL: no pg_hba.conf entry for host ...
```

`pg_hba.conf` controls which users can connect, from where, to which databases, and using which authentication method.

I should inspect the existing configuration before changing it.

Find the exact file:

```
SHOW hba_file;
```

---

# 23. `pg_hba.conf` — PostgreSQL's Connection Rules

Think of `pg_hba.conf` as a connection-access rule system.

It determines things such as:

```
WHO?
  │
  └── which PostgreSQL user?

FROM WHERE?
  │
  └── which host/IP?

TO WHAT?
  │
  └── which database?

HOW?
  │
  └── which authentication method?
```

Example structure:

```
host    all    furba    127.0.0.1/32    scram-sha-256
```

Meaning depends on the complete rule and PostgreSQL configuration, but conceptually:

```
host
 │
 ├── database = all
 ├── user = furba
 ├── address = 127.0.0.1/32
 └── authentication = scram-sha-256
```

After appropriate HBA changes, PostgreSQL may need a configuration reload.

# 24. `postgresql.conf`

`postgresql.conf` controls how the PostgreSQL server behaves.

Examples include:

```
shared_buffers

checkpoint_completion_target

work_mem

max_wal_size
```

I should inspect my current values rather than blindly copying settings from another machine.

Inside `psql`:

```
SHOW shared_buffers;
SHOW work_mem;
SHOW max_wal_size;
```

# 25. Configuration Contexts

Not every PostgreSQL setting can be changed in the same way.

|Context|What is needed|
|---|---|
|`internal`|Cannot normally be changed at runtime|
|`postmaster`|Full PostgreSQL restart|
|`sighup`|Configuration reload|
|`backend`|Next connection|
|`user`|Can apply at runtime|

So when changing a setting, I should check its context.

For example:

```
SELECT name, context
FROM pg_settings
WHERE name = 'shared_buffers';
```

---

# 26. `postgresql.auto.conf`

This file is automatically managed when I use:

```
ALTER SYSTEM
```

Example:

```
ALTER SYSTEM SET work_mem = '16MB';
```

PostgreSQL writes the setting into:

```
postgresql.auto.conf
```

I should generally let PostgreSQL manage this file instead of manually editing it.

# 27. Tablespaces

A tablespace allows PostgreSQL data to live outside the normal PGDATA directory.

Conceptually:

```
PGDATA
│
└── pg_tblspc
       │
       ├── link ─────► /data/fast_disk
       │
       └── link ─────► /data/slow_disk
```

Possible reasons:

- Use another disk
    
- Add storage
    
- Put certain data on faster storage
    

Two important tablespaces:

```
pg_default
    └── normal database storage

pg_global
    └── cluster-wide objects
```

# 28. PostgreSQL File Size and Filenodes

PostgreSQL can split a large relation across multiple files.

Conceptually:

```
123
123.1
123.2
```

These can represent successive segments of a relation.

The important lesson is:

```
SQL table name
      │
      ▼
PostgreSQL internal OID / filenode
      │
      ▼
physical files on disk
```

Don't manually rename or modify PostgreSQL data files.

Use PostgreSQL commands to manage PostgreSQL data.

# 34. Final Mental Model

I want to think of PostgreSQL like this:

```
                    LINUX
                      │
              systemctl manages
                      │
                      ▼
                POSTGRESQL
                      │
                      ▼
                   CLUSTER
                      │
          ┌───────────┼───────────┐
          ▼           ▼           ▼
      template0   template1     mydb
                                  │
                                  ▼
                                users
                                  │
                            ┌─────┴─────┐
                            ▼           ▼
                           id          name


On disk:

/var/lib/postgresql/16/main/
              │
              ├── base/
              │     └── OID directories/files
              │
              ├── pg_wal/
              ├── global/
              ├── pg_tblspc/
              ├── postgresql.conf
              ├── postgresql.auto.conf
              └── pg_hba.conf


Tools:

psql       → talk to PostgreSQL
pg_ctl     → control a PostgreSQL cluster
oid2name   → understand OIDs/filenodes
pg_dump    → backup
pg_restore  → restore
systemctl  → manage the Linux PostgreSQL service
```

**Core idea:**

> `systemctl` manages the Linux service, `pg_ctl` controls a PostgreSQL cluster, `psql` talks to a database, and PGDATA is where that cluster's physical data and configuration live.
